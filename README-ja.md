AWS 2-Tier セキュアアーキテクチャ構築および VPC 内 DB 接続トラブルシューティングガイド
概要 (Summary)
現代のパブリッククラウドおよびハイブリッドクラウド環境において、中核となるデータ資産のネットワーク隔離とアクセス制御はインフラセキュリティの最優先事項です。本ガイドは、AWS 環境においてベストプラクティスに準拠した 2-Tier 隔離ネットワーク（2-Tier Architecture）をゼロから構築した全工程を記録したものです。カスタム VPC によるパブリック/プライベートサブネットの分離と、ネストされた厳格なセキュリティグループ（Security Groups）ポリシーの設定により、Amazon RDS データベースの高度な保護を実現し、パブリックインターネットからの直接アクセスを完全に遮断しました。また、構築過程で発生したネットワークタイムアウト（Timeout）やクロスプラットフォームにおける鍵権限検証のトラブルシューティング（Troubleshooting）の事例、および検証完了後の標準的なリソースクリーンアップとコスト管理手順についても詳細に記載しています。


前提条件 (Prerequisites)
アクティブな AWS アカウント（AWS 無料利用枠の利用を推奨）。
安全なログインに使用する非対称暗号鍵ペア（.pem 形式のキーペア）。
基本的なネットワークアクセス権限を持つローカル Windows OS 環境および CMD / PowerShell ターミナル。


アーキテクチャ構成 (Architecture)
本ソリューションでは、高可用性と高セキュリティを兼ね備えたネットワークトポロジ設計を採用しています：
カスタム VPC (Virtual Private Cloud)： 2つのアベイラビリティゾーン（Multi-AZ）にまたがる物理的に隔離されたネットワークコンテナを構成。
サブネット設計 (Subnets)： 2つのパブリックサブネット（Public Subnets、Internet Gateway 経由でインターネットに接続）と2つのプライベートサブネット（Private Subnets、パブリックルーティングなし）をデプロイ。
ファイアウォール戦略： 2重の防御線を構築。フロントエンドは Web-SG セキュリティグループでパブリック SSH トラフィックのインバウンドを制御し、バックエンドは DB-SG セキュリティグループで Web-SG からの 3306 端口（MySQL）の内部トラフィックのみを許可。

![VPCとサブネット構成の確認画面](./AWS-Project/images/vpc-subnets-config.png)

使用ツール (Tools)
Amazon VPC： 基礎となるネットワーク隔離環境とルーティング制御を提供。
Amazon EC2： パブリックサブネットにデプロイし、踏み台サーバー（Bastion Host）として内部ネットワークへアクセスするための唯一の正規かつ暗号化された計算ノードとして機能。
Amazon RDS (MySQL)： 中核となるデータストレージエンジン。プライベートサブネットにデプロイし、外部インターネットからの直接アクセスを完全に遮断。
AWS Security Groups： インスタンスレベルの仮想ファイアウォールとして機能し、インバウンドおよびアウトバウンドの細粒度なトラフィックフィルタリングを実行。



構築ステップ (Implementation Steps)
1. ネットワーク基盤とセキュリティ隔離の設定
VPC の作成および AZ の割り当て完了後、デフォルトルートテーブルを設定してパブリックサブネットが IGW (Internet Gateway) 経由で外部ネットワークにアクセスできるようにします。セキュリティグループを設定して最小権限の原則に基づいたアクセス制御を実現します：
フロントエンドセキュリティグループを設定し、SSH (TCP 22) アクセス元を制限。
バックエンド DB セキュリティグループを設定し、フロントエンドセキュリティグループがアタッチされたインスタンスからの MySQL (TCP 3306) アクセスのみを許可。

2. コンピューティングおよびデータリソースのデプロイ
パブリックサブネットに EC2 インスタンスを起動し、ログイン用の .pem 鍵をバインドします。プライベートサブネットに Amazon RDS インスタンスを起動し、管理者ユーザー名とパスワードを設定した上で、指定した内部セキュリティグループに割り当てます。

3. OS レベルの環境初期化
Windows ローカルの CMD ターミナルから SSH コマンドを実行し、EC2 インスタンスとの暗号化トンネルを確立します。Amazon Linux 環境にログイン後、パッケージマネージャーを使用して軽量なデータベースクライアントツール（MariaDB Client）をインストールします。

![EC2ターミナルで Complete! が表示されたDBクライアントのインストール成功画面](./AWS-Project/images/ec2-db-client-installed.png)

4. 接続検証 (Verification)
RDS に割り当てられた内部 Endpoint、ポート、および認証情報を使用し、EC2 から内部データベースへの接続を発行・検証します。

![MySQLへのログイン成功画面](./AWS-Project/images/mysql-connect-success.png)



トラブルシューティング (Troubleshooting)

アーキテクチャの構築および接続テストの過程において、以下の2つのネットワーク接続障害を切り分け、解決しました：

Issue 1：EC2 インスタンスへの SSH 接続タイムアウト (Connection Timed Out)
事象： ローカル環境からパブリックサブネット上の EC2 インスタンスへ SSH 接続を試みた際、ターミナルが長時間応答なしとなり、最終的に Connection timed out エラーが発生。
原因： フロントエンドセキュリティグループのインバウンドルール（Inbound Rule）がセキュリティ対策として「My IP」に設定されていました。しかし、ローカル環境のプロバイダから割り当てられたパブリック IP アドレスが動的に変更されたため、AWS のセキュリティグループによってトラフィックが破棄（Drop）されていました。
解決策： 切り分けの一環として、セキュリティグループの SSH インバウンドルールの送信元（Source）を一時的に Anywhere-IPv4 (0.0.0.0/0) に変更。ネットワーク導通を確認後、最新のローカル IP に再設定してアクセス制御を強化しました。

![セキュリティグループのInbound Ruleを0.0.0.0/0に変更した画面](./AWS-Project/images/sg-inbound-rule-change.png)

Issue 2：非対称暗号鍵のパーミッション拒否 (Bad Permissions)
事象： ネットワークの導通確認後、SSH クライアント側で接続が拒否され、「WARNING: UNPROTECTED PRIVATE KEY FILE!」および「Bad permissions」のエラーが発生。

![Windows CMDでのWARNINGおよびPermission deniedエラー画面](./AWS-Project/images/ssh-bad-permissions-error.png)

原因： Windows NTFS ファイルシステムにおいて、ダウンロードした .pem 鍵ファイルが親ディレクトリの寛容な権限を継承していました。これにより、現在のユーザー以外の他のユーザーにも鍵ファイルの読み取り権限が付与されている状態となり、SSH クライアントの安全装置が作動して接続が自動遮断されました。
解決策： AWS EC2 公式トラブルシューティングガイドに従い、Windows のファイル権限をリセットしました。CMD で icacls コマンドを実行：
1. icacls RDS-test-key.pem /inheritance:r を実行し、当該ファイルのすべての継承権限を削除。
2. icacls RDS-test-key.pem /grant 52433:F を実行し、現在のアクティブユーザー（52433）にのみフルコントロール（Full Control）権限を付与。
パーミッション修正後に再度 SSH コマンドを実行したところ、警告を回避して正常に EC2 環境へログインできました。



クリーンアップ / コスト管理 (Cleanup / Cost Management)

アーキテクチャの接続検証完了後、FinOps（クラウド財務管理）の観点およびコスト最適化に基づき、不要な課金を防ぐため迅速にリソースのクリーンアップを実施しました：
1. スナップショットなしでの DB ノード削除： RDS インスタンスを削除し、最終スナップショット（Snapshot）の作成をスキップ。
2. コンピューティングノードの削除： EC2 コンソールからインスタンスのステータスを「Terminate（削除）」に変更。
3. ネットワーク資産の解放： Elastic IP (EIP) コンソール画面から、インスタンス削除に伴い未割り当て状態となった EIP を完全に解放し、クラウド資産の不要な維持費の発生を確実に防ぎました。
